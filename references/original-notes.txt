2. Recommended game design
Box Blitz — Two-Player Memory Battle
Game Design & Technical Specification — Version 1.0

Objective: Build an original, browser-based, two-player competitive memory game inspired by the cube-counting mechanic from Dr. Kawashima's Brain Training.

Platforms: Desktop browsers first, mobile/tablet second.

Core principle: Both players see the same arrangement of 3D cubes for a short period, then compete to recall the correct total.

A. Game modes
Mode	Description
Quick Match	10 rounds, increasing difficulty
Full Match	20 rounds, increasing difficulty
Endless	Unlimited procedurally generated levels
Practice	Single player, choose difficulty
Custom Challenge	Play personally designed or imported levels
Custom Match	Configure level range, timers, round count, and progression
Two-player local multiplayer is the primary mode. Both players share one screen and keyboard or use separate controllers.

An optional future update can add online multiplayer with private room codes.

B. Core round loop
Every round follows this state machine:

1. Ready (1 second)

Display the upcoming round number.

Reset both answer counters to zero.

Display an empty isometric grid.

2. Preview (1–3 seconds)

An arrangement of cubes becomes visible simultaneously.

The player must quickly identify the total number of individual cubes.

The arrangement remains fixed during the preview.

Both players see exactly the same image.

3. Memorization ends

Cubes disappear with a quick fade.

The empty grid remains, matching the reference game.

Prompt changes to "How many cubes were there?"

Both players can now input their answers.

4. Answer phase (maximum 8 seconds)

Players independently increment their counters.

Each player presses a separate button to lock their answer.

A submitted answer cannot be changed.

One player's submission must not interfere with the other player's input.

5. Reveal (2 seconds)

Reveal the original cube formation again.

Show the correct total prominently.

Show each player's guess and whether it was correct.

Highlight the winner of the round.

Animate the updated scores.

6. Transition (0.7 seconds)

Advance automatically to the next round.

If both players submit early, end the answer phase immediately. If neither submits in time, both score zero.

C. Two-player control system
Action	Player 1	Player 2
Increase answer by 1	Z	N
Confirm answer	X	M
Keyboard alternative	A / S	K / L
Gamepad	Shoulder button	Shoulder button + confirm
Use the Z/X/N/M default from the existing browser adaptation.

Controls should be remappable in Settings.

On mobile, each player gets two large touchscreen buttons on opposite sides of the screen.

Important: Every key press increments exactly once. Holding a key must not accidentally produce dozens of counts through operating-system auto-repeat.

Offer two input modes:

Classic Counter: Repeated button presses increase the displayed number.

Direct Entry: Players can type a numeric answer instead.

Both players must use the same input mode in competitive matches to preserve fairness.

D. Visual layout
Match the basic composition from the TikTok video while using original branding and assets.

Landscape 16:9 composition

White or pale neutral background.

Question at the upper center.

Large isometric cube grid in the middle.

Player 1 counter and controls at bottom left.

Player 2 counter and controls at bottom right.

Round indicator and match scores at the top.

Distinct player accents, such as blue and coral.

The playing field should use a fixed isometric viewing angle rather than a perspective camera.

Cubes need thin, dark outlines and three distinguishable visible faces. Their tops and sides should be visually readable even when stacked.

Avoid unnecessary particle effects or moving cameras during the memorization phase.

E. Level difficulty system
These are proposed balancing values, not verified Nintendo timings.

Tier	Cubes	Maximum stack	Preview time	Spatial pattern
1 — Beginner	3–5	1	3.0 s	Small, simple groups
2 — Easy	5–8	2	2.6 s	Adjacent clusters
3 — Medium	8–12	2	2.2 s	Multiple groups and short stacks
4 — Hard	12–18	3	1.8 s	Irregular layouts and tall stacks
5 — Expert	18–24	4	1.5 s	Complex arrangements and partial occlusion
Difficulty should depend on more than total cube count.

Consider:

Number of occupied grid positions.

Number of disconnected clusters.

Number and height of vertical stacks.

Cube count.

How much one stack visually overlaps another.

Viewing duration.

Repetition or symmetry that makes counting easier.

A tightly grouped arrangement of 12 cubes may be easier than 9 cubes scattered across multiple stacks.

F. Twenty-round level progression
A standard full match should follow five four-round chapters.

Rounds	Tier	Intended experience
1–4	Beginner	Learn to count quickly
5–8	Easy	Introduce vertical stacks
9–12	Medium	Require mental grouping
13–16	Hard	Increase complexity and memory pressure
17–20	Expert	Competitive final stretch
For a 10-round Quick Match, use two rounds from each tier.

Adaptive difficulty (optional): Every three rounds, evaluate both players together. If they are consistently correct and fast, increase challenge slightly. If both consistently fail, decrease challenge.

Never generate separate difficulty levels for opposing players in the same round.

G. Procedural level generation
Levels should be generated from a deterministic seed so that any level can be replayed and shared.

Grid model
Use a configurable isometric board, defaulting to 5 × 5 cells.

Each cell stores a nonnegative integer height:

0 = empty

1 = one cube

2 = two vertically stacked cubes

3 = three cubes

4 = four cubes

The correct answer is always the sum of all cell heights.

All stacks must start on the ground and be vertically contiguous. Floating cubes are not permitted in normal mode.

Generator process
Receive difficulty tier and random seed.

Pick a target cube count within the tier's range.

Determine an occupied-cell count and desired number of clusters.

Choose grid cells using a mixture of adjacency-based growth and scattered placement.

Distribute the remaining cubes as vertical stacks within the height limit.

Reject arrangements that hide too much information from the camera.

Compute and validate the correct answer.

Assign a difficulty score to the finished arrangement.

Compare the score with the desired difficulty band.

Accept the puzzle or regenerate.

Geometry and fairness
A cube can be partially concealed by a taller neighboring stack. This should introduce spatial reasoning rather than make the answer unknowable.

For Beginner through Medium, avoid completely hidden columns. In higher tiers, allow partial occlusion only where the total remains reasonably inferable.

The generator should reject:

Unreadable cube edges.

Fully hidden structures without sufficient visual cues.

Layouts exceeding the allowed grid.

Repeated arrangements within the recent level history.

Levels whose actual cube count falls outside the tier's allowed range.

The generator must save the seed and heights matrix, not a screenshot of the puzzle.

Variety templates
Support at least eight pattern families:

Scattered single cubes.

Straight lines.

Rectangular groups.

Multiple disconnected groups.

Short vertical towers.

Staircase-height formations.

Irregular clusters.

Mixed towers and isolated cubes.

Randomly combine pattern templates at higher difficulties.

H. Scoring and match winner
Accuracy is the highest priority. Speed provides a smaller competitive advantage.

Suggested scoring:

Correct answer: +100 points.

Fastest correct answer when both players are correct: +10 bonus.

Incorrect answer: 0.

No answer before timeout: 0.

Answers submitted within 100 milliseconds of each other are considered a speed tie.

Record response time from the start of the answer phase, not from the beginning of the cube preview.

The player with the highest total score wins the match.

If both players finish with equal scores, compare:

Total correct answers.

Average time for correct answers.

If still tied, declare a draw or offer a tiebreaker round.

Provide a final match summary with wins, accuracy, average response time, and hardest correctly completed level.

I. Level editor
Include a fully functional built-in level creation tool.

Editor interface:

Interactive isometric grid.

Click a cell to increase stack height.

Right-click or use a decrement tool to remove height.

Paint/drag controls for creating arrangements.

Clear board, undo, redo, and randomize buttons.

Set board dimensions and maximum stack height.

Set preview and answer durations.

Set difficulty category and optional level name.

Live display of total cubes.

Preview and testing:

Play the level exactly as players will encounter it.

Test it in single-player or two-player mode.

Automatically flag invalid or excessively occluded arrangements.

Estimate difficulty based on structural features.

Saving:

Save custom levels locally.

Export and import level packs as JSON.

Generate a shareable level code or URL.

Load a custom pack into a multiplayer match.

Allow a custom pack to shuffle its levels or play them in order.

The browser game should also support infinite procedurally generated levels, independently of hand-authored content.

J. Content progression
Create three starter packs with 20 levels each:

First Glance: Mostly small flat formations.

Stack Attack: Tall cubes, depth, and grouping challenges.

Memory Sprint: Shorter visibility periods and more complex shapes.

Add a procedural Endless pack that generates new rounds indefinitely.

Store predesigned levels and procedural seeds using a common level format so the same game engine handles both.

K. Technical architecture
Recommended stack

React + TypeScript.

Vite for development/build.

Three.js with an orthographic camera for the cube renderer.

CSS for HUD, counters, and menus.

Web Audio API for sound effects.

IndexedDB or localStorage for settings, match history, and saved levels.

Vitest for deterministic generator and scoring tests.

Separate the game into five systems:

Level Engine: Seeded generation, authored levels, validation.

Renderer: Isometric cubes, grid, visual transitions.

Game Controller: Timed phases and match flow.

Input Manager: Independent controls and submission locking.

Persistence: Level packs, settings, statistics, and progression.

Game logic must not be coupled directly to rendering code.

Keep everything client-side for the local multiplayer version. No user account, backend, or online service should be required.

L. Minimum viable product
The initial release must include:

Two players using one keyboard.

A 5 × 5 isometric cube board.

Procedural cube formation generation.

Five difficulty tiers.

Preview, disappearance, answer, and reveal phases.

Independent answer counters.

Accuracy-based scoring.

10- and 20-round match formats.

Functional level editor.

Import/export custom levels.

Responsive landscape presentation.

Settings for preview duration and controls.

Acceptance criteria

Both players always see identical puzzle content.

The answer always matches the sum of the generated cube heights.

Players cannot edit a locked answer.

Holding a key never causes unwanted repeated input.

Puzzle generation is reproducible from the same seed.

Returning from an inactive browser tab cannot cause rounds to skip unpredictably.

A completed match can be restarted without reloading the page.

Custom levels remain playable after a fresh browser session.

No hidden cube makes an ordinary-difficulty level impossible to count.

M. Future improvements
After the core game is stable:

Online private matches using room codes.

Daily challenges with identical seeds for everyone.

Leaderboards and personal records.

More level pattern generators.

Accessibility settings, including high contrast and adjustable timings.

Gamepad support and separate-phone controller support.

Optional alternative modes such as counting moving objects, memorizing sequences, or tracking changes in cube quantity.

The first release should concentrate on making the simple counting competition satisfying before adding additional minigames.

4. What I would change in our specification
A. Start with flat cubes, not tall towers
The screenshots show small arrangements with relatively simple silhouettes. Our original specification progresses rapidly toward large, four-cube-high towers and partially hidden columns.

That might be a fun variation, but I wouldn't make it the default.

Instead, use three structural categories:

Classic: Small arrangements, one cube high, similar to the official examples.

Intermediate: Irregular clusters with small height changes.

Advanced: Taller formations, occlusion, and harder three-dimensional reasoning.

This keeps the recognizable Nintendo-style game separate from our more elaborate puzzle extensions.

B. Use the original's two distinct cube appearances
During the memorization phase, render white cubes with gray shaded sides and dark outlines. During the reveal, highlight the answer cubes in green.

That detail is useful because it keeps the memory challenge neutral while making the answer reveal satisfying and immediately understandable.

C. Prioritize recognition speed rather than mathematical complexity
The core challenge is recognizing a spatial pattern in a glance. A smaller irregular arrangement can be harder to recognize than a larger rectangular formation.

I'd therefore revise the level generator to track not only cube count and stack heights, but also:

Whether the arrangement forms a familiar shape.

How many separate groups are present.

How compact or scattered the groups are.

Whether the arrangement can be counted using obvious rows.

That would produce more natural difficulty variation than simply adding cubes every round.

D. Keep Nintendo-style controls as the competitive default
The original uses the shoulder buttons like a mechanical tally counter: repeatedly press one button to build an answer, then press another to confirm.

For a browser game, I would preserve this as the default competitive method rather than using direct number entry, because the physical act of counting is part of the challenge.

5. Revised core design
Recommended faithful-mode round sequence

Ready: Both players start with an answer of zero.

Display: White/gray isometric cubes appear briefly on a shared grid.

Hide: All cubes disappear, leaving the empty grid visible.

Count: Both players independently increment their numeric counters.

Submit: Each player locks their answer.

Reveal: Correct number appears and the arrangement returns with answer feedback.

Score: Correctness and speed determine the winner, followed by the next round.

I would implement the sequence exactly in that order, but retain configurable durations until we can measure them from recordings.

My conclusion: The underlying specification is aligned with the original game's main mechanics. The biggest improvement is to make the initial release much more restrained visually, using small, simple isometric formations and the distinctive two-button counting controls.

Then add taller stacks, advanced layouts, procedural difficulty and the level editor as features that distinguish your browser game from Nintendo's version.
